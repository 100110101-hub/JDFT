# DFT-D4 dispersion data — staging provenance

This directory collects everything needed to implement Grimme's **DFT-D4**
(charge- and coordination-number-dependent London dispersion, `dftd4`) in Rust,
together with byte-level provenance for every number. **No value in the JSON
files was typed by hand**: they are generated by the scripts here from verbatim
copies of the upstream sources under `raw/`.

```
_d4_staging/
├── PROVENANCE.md            this file
├── raw/                     verbatim upstream files, one directory per repository
├── raw_manifest.json        URL + size + sha256 of every file in raw/
├── eeq_elements.json        per-element parameters for Z = 1..36
├── eeq2019.json             EEQ(2019) charge model parameters + equations, Z = 1..103
├── damping_parameters.json  per-functional damping parameters (bj-eeq-atm)
├── reference_systems.json   D4 reference systems, reference C6, r4r2, CN parameters
├── d4_parse.py              shared parsing helpers (stdlib only)
├── extract_d4_data.py       generates eeq_elements.json, damping_parameters.json,
│                            raw_manifest.json
├── extract_d4_reference.py  generates reference_systems.json
├── extract_eeq2019.py       generates eeq2019.json
└── validate_d4_data.py      reproduces official dftd4 values from the JSON only
```

## 4. The energy expression actually implemented

### 4.1 Coordination number (D4 CN)

`dftd4/src/dftd4/ncoord.f90` builds a `cn_count%dftd4` evaluator with
`kcn = 7.5` (`default_kcn`, line 30) and no CN cap (`cut` is never passed).
mctc-lib supplies the per-pair counting function
(`mctc/ncoord/erf.f90:106-122`):

```fortran
      rc = (self%rcov(izp) + self%rcov(zjp))
      count = 0.5_wp * (1.0_wp + erf(-self%kcn*(r-rc)/rc**self%norm_exp))
```

with `directed_factor = 1` and the electronegativity factor of the D4 variant
(`mctc/ncoord/erf/dftd4.f90:116-128`):

```fortran
      en_factor = k4*exp(-(abs(self%en(izp)-self%en(zjp)) + k5)**2.0_wp/k6)
      ! k4 = 4.10451, k5 = 19.08857, k6 = 2*11.28174**2
```

so

```
CN_i = sum_{j != i} en_factor(i,j) * 0.5 * (1 + erf(-kcn*(r_ij - rc)/rc)),
       rc = rcov_i + rcov_j,  kcn = 7.5,  en_factor from Pauling EN
```

The radii are `covalent_rad_d3 = 4/3 * covalent_rad_2009` (Pyykkö/Atsumi,
metals already −10 %); `get_covalent_rad` returns the **already scaled** array
(`data/covrad.f90:64-65, 96`), so `ncoord.f90` applies no further factor.
The real-space CN cutoff is `cn_default = 30.0` bohr (`cutoff.f90:27`); pairs
with `r < 1e-6` are skipped, so an isolated atom has CN = 0.

### 4.2 EEQ(2019) charges

`model/d4.f90:196` creates `new_eeq2019_model`, i.e. the multicharge model whose
parameters are staged in `eeq2019.json`. The linear system is
(`model/eeq.f90`):

```fortran
      if (iat == jat) then
         tmp = self%eta(izp) + sqrt2pi / self%rad(izp)
      else
         gam = 1.0_wp / (self%rad(izp)**2 + self%rad(jzp)**2)
         tmp = erf(sqrt(r2 * gam)) / sqrt(r2)
      end if
...
      tmp = self%kcnchi(izp) / sqrt(ptr%cn(iat) + reg)
      xvec(iat) = -self%chi(izp) + tmp * ptr%cn(iat)
...
      amat(mol%nat + 1, 1:mol%nat + 1) = 1.0_wp
      amat(1:mol%nat + 1, mol%nat + 1) = 1.0_wp
      amat(mol%nat + 1, mol%nat + 1) = 0.0_wp
```

i.e. `A q = x` with

```
A_ii = eta_i + sqrt(2/pi)/rad_i
A_ij = erf(r_ij / sqrt(rad_i^2 + rad_j^2)) / r_ij
x_i  = -chi_i + kcnchi_i * CN_i / sqrt(CN_i + 1e-14)
x_{N+1} = Q_total,  A_{N+1,i} = A_{i,N+1} = 1,  A_{N+1,N+1} = 0
```

The extra row/column of ones is the **Lagrange multiplier enforcing
Σ q_i = Q_total**. The EEQ CN is the *plain* erf CN (`cn_count%erf`) with the
same `kcn = 7.5`, cutoff 25 bohr, and it **is** capped at 8
(`cn_max = 8.0`, smooth `log(1+exp(8)) - log(1+exp(8-CN))`). The `rad` are
static: no charge or CN scaling enters the kernel (`eeq.f90:350, 355`).

### 4.3 Reference weights (CN- and charge-dependent)

`model/d4.f90:284-331` (and `model/utils.f90:37-60`):

```fortran
                wf = igw * self%wf
                gw = weight_cn(wf, cn(iat), self%cn(iref, izp))
...
            gwvec(iref, iat, 1) = gwk * zeta(self%ga, gi, self%q(iref, izp)+zi, q(iat)+zi)
```

with `zi = zeff(izp)`, `gi = eta(izp) * gc`, `weight_cn = exp(-wf*(CN-CN_ref)^2)`
and

```fortran
      zeta = exp( a * ( 1.0_wp - exp( c * ( 1.0_wp - qref/qmod ) ) ) )
```

So each reference system weight is

```
w(ref; i) ~ [sum_igw exp(-igw*wf*(CN_i - CN_ref)^2)] / normalization
            * zeta(ga, eta_i*gc, clsq(ref,Z_i) + zeff_i, q_i + zeff_i)
```

**The charge enters shifted by `zeff`** on both sides of the scaling function;
`ga = 3.0`, `gc = 2.0`, `wf = 6.0` (`model/d4.f90:65-71`). The CN used in the
weights is `refcovcn` (`d4.f90:174` → `reference.f90:158`), while `refcn`
only sizes the Gaussian weights via `set_refgw` (`reference.f90:187-203`).
Element hardness here is the *D4* table in `data/hardness.f90`, not the EEQ η.

### 4.4 Reference polarizabilities and C6

`reference.f90:330-365` scales the tabulated 23-point polarizabilities:

```fortran
          iz = get_effective_charge(is)
          aiw = sscale(is)*secaiw(:, is) &
             &    * zeta(ga, get_hardness(is)*gc, iz, clsh(ir, num)+iz)
          alpha(:, ir) = max(ascale(ir, num)*(alphaiw(:, ir, num) &
             &            - hcount(ir, num)*aiw), 0.0_wp)
```

and `model/d4.f90:228-231` integrates the Casimir–Polder integral:

```fortran
               aiw(:) = d4%aiw(:, iref, isp) * d4%aiw(:, jref, jsp)
               c6 = thopi * trapzd(aiw)
               d4%c6(jref, iref, jsp, isp) = c6
               d4%c6(iref, jref, isp, jsp) = c6
```

with `thopi = 3/pi` (`d4.f90:104`) and a trapezoid rule over 23 imaginary
frequencies (`model/utils.f90:81-122`). The result is exactly symmetric, so the
"first index = higher-Z element" question is moot; both triangles are written.
`reference_systems.json` stores the raw `alphaiw`, the scaled `alphaiw_eeq`, and
the derived C6 matrices for all element pairs.

### 4.5 Two-body energy and damping

`damping/rational.f90:184-200`:

```fortran
          rrij = 3*r4r2(izp)*r4r2(jzp)
          r0ij = self%a1 * sqrt(rrij) + self%a2
          c6ij = c6(jat, iat)
...
            t6 = 1.0_wp/(r2**3 + r0ij**6)
            t8 = 1.0_wp/(r2**4 + r0ij**8)
            edisp = sw * (self%s6*t6 + self%s8*rrij*t8)
            dE = -c6ij*edisp * 0.5_wp
```

Because each pair contributes `dE` to both atoms of an `iat >= jat` loop, the
total two-body energy is

```
E2 = -sum_{i<j} C6_ij * [ s6/(R_ij^6 + r0_ij^6) + s8*rrij_ij/(R_ij^8 + r0_ij^8) ]
rrij_ij = 3 * r4r2_i * r4r2_j
r0_ij   = a1 * sqrt(rrij_ij) + a2
```

`sw` is the quintic smooth-cutoff switch, `1` for molecules inside the 60 bohr
default cutoff (`cutoff.f90:30, 74-114`).

**`alp` is not used by the two-body term.** The only `self%alp` uses in
`rational.f90` are the ATM delegation (`411-412`, `461-462`) and the ATM
exponent (`594`, `649`). `alp = 16.0` is the default and applies only to the
three-body damping.

**The two-body C6 is weighted with the actual EEQ charges** (via `q + zeff` in
the zeta factor, §4.3) — this is the entire "charge dependence" of the damping:
there are no `s6q/s8q/a1q/a2q` coefficients.

### 4.6 Three-body ATM term (on by default)

`damping/atm.f90:621-635`:

```fortran
                   r2 = r2ij*r2ik*r2jk
                   r1 = sqrt(r2)
                   r3 = r2 * r1
                   r5 = r3 * r2
                   fdmp = 1.0_wp / (1.0_wp + 6.0_wp * (r0 / r1)**alp3)
                   ang = 0.375_wp*(r2ij + r2jk - r2ik)*(r2ij - r2jk + r2ik) &
                      & *(-r2ij + r2jk + r2ik) / r5 + 1.0_wp / r3
                   rr = ang*fdmp
                   dE = rr * c9 * triple * third * sw
                   energy_local(iat) = energy_local(iat) - dE
                   energy_local(jat) = energy_local(jat) - dE
                   energy_local(kat) = energy_local(kat) - dE
```

with `c9 = -s9*sqrt(|C6_ij C6_ik C6_jk|)`, `r0 = r0ij*r0ik*r0jk`,
`alp3 = alp/3`, `third = 1/3`, i.e. per distinct triple
`E3 -= rr*c9 = ang*fdmp*s9*sqrt(|C6_ij C6_ik C6_jk|)`.

`get_rational_damping` prefers the `bj-eeq-atm` table whose `dftd_param`
defaults `s9 = 1.0`, so **the ATM term is on by default**; `s9 = 0` turns it
off (`atm.f90:504`). A two-body-only variant exists (`bj-eeq-two`, s9 = 0, in
`assets/parameters.toml`).

**Important implementation detail (validated):** `disp.f90:139-141` resets
`q(:) = 0` and rebuilds the C6 *before* calling the three-body term, so the ATM
term uses **reference weights evaluated at q = 0**, while the two-body term uses
the charge-weighted C6. Using the charge-weighted C6 for ATM makes the energy
off by up to 30 %; with `q = 0` the staged data reproduces the official energies
to 3e-8 relative (§7).

## 7. Validation against the official implementation

`validate_d4_data.py` re-implements the pipeline **using only the staged JSON
files** and compares with values produced by the official dftd4 4.3.1 Python
bindings, which are already committed in the repository
(`qwb-core/crates/qwb-scf/tests/reference/d4_properties.csv` and
`d4_dispersion.csv`, generated by `scripts/dftd4_dispersion_reference.py`).
9 dimers (water, ammonia, methane, methanol, benzene stacked/displaced, CO2,
HF, ethyne) are covered.

| quantity | max abs. deviation | max relative deviation |
|---|---|---|
| coordination number | 8.6e-08 | 1.8e-08 |
| EEQ charge | 3.0e-08 | 3.7e-08 |
| polarizability | 1.4e-07 | 1.5e-08 |
| C6 to first atom | 1.2e-06 | 2.9e-08 |
| two-body + ATM energy (5 functionals) | 3.1e-09 Ha | 3.2e-08 |

The residual is explained by the upstream precision: `alphaiw` is stored with
7 decimals and the `r4_over_r2` table has 4–5 significant digits, so ~1e-8
relative is the attainable agreement.

Run it with `python validate_d4_data.py` (needs the repository layout; it reads
the reference CSVs but no network).

## 8. Regeneration

```bash
cd qwb-data/dispersion/_d4_staging
python extract_d4_data.py            # writes the three element/damping files
python extract_d4_reference.py       # writes reference_systems.json
python extract_eeq2019.py            # writes eeq2019.json
python validate_d4_data.py           # cross-check against official dftd4 values
```

Each generator has a `--check` mode that regenerates in memory and compares
byte-for-byte with the file on disk, exiting non-zero on any difference:

```bash
python extract_d4_data.py --check
python extract_d4_reference.py --check
python extract_eeq2019.py --check
```

Re-downloading `raw/` is not automated (no network use is required for
regeneration). The pinned URLs are in `raw_manifest.json`; a fresh fetch must
reproduce the sha256 values there.

## 9. What is still ambiguous / not covered

1. **No charge-response damping coefficients exist upstream.** There is no
   `s6q`, `s8q`, `a1q` or `a2q` anywhere in dftd4 v4.3.1 (nor in the older
   v3.0.0 parameter table, which was checked and only ever enumerated M06-2X
   without parameters). The charge dependence of D4 enters (a) through the EEQ
   charges in the reference weights (`q + zeff`) and (b) through the
   charge-scaled reference polarizabilities. `damping_parameters.json` records
   these fields as `null` with an explanation rather than inventing values.
2. **M06-2X has no D4 parameter entry upstream.** The functional enumerator and
   the damping tables in `param.f90` contain M06 and M06-L only;
   `assets/parameters.toml` has no block for it either, and the repository's own
   D4 reference script records the runtime error `Functional 'm06-2x' not
   known`. No values are provided.
3. **`alp` does not enter the two-body term.** It is used exclusively by the
   ATM three-body damping (exponent `alp/3`). Anyone expecting a
   `1/(1+(r0/r)^alp)` two-body damping will get wrong numbers; the implemented
   form is the rational/BJ form with fixed powers 6 and 8 (power-of-six
   denominators), which is exactly what `rational.f90:195-196` evaluates.
4. **Reference C6 is not stored upstream.** It is computed at model setup from
   `alphaiw` and depends on the default `ga`/`gc` (3.0/2.0). If the
   implementation ever exposes `ga`/`gc`, the staged C6 matrices must be
   regenerated (or the scaling recomputed).
5. **ATM term defaults.** It is on by default (`s9 = 1.0`) for the standard
   parameter set; turning it off is a parameter choice (s9 = 0), not the
   default. It also uses C6 built with `q = 0`, unlike the two-body term — easy
   to get wrong, and worth an explicit unit test.
6. **Two different coordination numbers** are in play: the D4 CN
   (EN-weighted, `rcov = 4/3·Pyykkö`, cutoff 30 bohr, no cap) and the EEQ CN
   (plain erf, same 4/3 radii, kcn 7.5, cutoff 25 bohr, smoothly capped at 8).
   They are not interchangeable.
7. **`r4r2` has two meanings upstream.** `data/r4r2.f90` stores the raw
   `<r4>/<r2>` table (`r4_over_r2`, e.g. 8.0589 for H), but `get_r4r2_val`
   returns the derived `sqrt(0.5·<r4>/<r2>·sqrt(Z))` (e.g. 2.00735 for H),
   which is what `rrij = 3·r4r2_i·r4r2_j` uses. Both are staged. The derived
   values are **identical to the D3 `r4r2` table already in `d3bj.yaml` for all
   36 elements** (verified), despite the different raw arrays — the parent's
   assumption that they might differ does not hold for H–Kr.
8. **Element range.** The JSON extracts stop at Z = 36 (the staged scope);
   dftd4 itself supports Z ≤ 103 (EEQ `max_elem = 103`; the D4 model rejects
   104–111 explicitly, `d4.f90:106-112`) and `reference.inc` contains data up to
   Z = 110. Extending is a matter of raising `NTARGET`/`NELEM` and re-running
   the scripts; nothing else changes.
9. **Unit constant.** The upstream conversion is mctc-lib's CODATA-2018
   `aatoau = 1.8897261257783122`; the repository currently uses
   `BOHR_PER_ANGSTROM = 1.889726089838572` (CODATA-2014), a 1.9e-8 relative
   difference. Pick one for the loader; at 1e-8 level it does not matter, but
   the validation above used the upstream constant.
10. **Not staged:** gradients, Hessians, virials, periodic/Wigner–Seitz
    handling, the smooth cutoff width, and the alternative charge models
    (`eeqbc2025`, GFN2-xTB reference charges, `d4s`). The `damping_parameters.json`
    model block documents the energy expressions only.
11. **`wfpair.f90` is not used by the D4 energy path.** It is exported by
    `data.f90` but no staged module calls `get_wfpair_val`; it is kept only
    because `data.f90` re-exports it. It is not needed for `d4.yaml`.
12. **M06 (plain) vs M06-L.** Only M06-L was requested and staged; upstream also
    has an M06 entry. Adding it is a one-line change in `extract_d4_data.py`.
